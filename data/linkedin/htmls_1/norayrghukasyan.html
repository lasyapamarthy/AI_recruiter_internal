Every time you access it, Node proxies that call to the underlying environment variables via the OS. That means every lookup involves a C++ binding, not a cheap object property access. For low-traffic apps, it's noise. At scale? It'll kill your P99s. (99th percentile of latency) If you’re doing this inside a tight loop, a hot middleware, or even worse inside a function called hundreds of times per request, you’re paying an avoidable tax on every single request. We’re talking about microseconds, but at 10k RPS (Requests Per Second), a microsecond here, a microsecond there... and your P99s start looking ugly fast. I’ve seen real-world latency drops just by hoisting process.env reads out of request handlers. What to do instead? - Cache your environment variables at startup. - Don’t read from process.env inside code that runs per request, per loop, or in critical paths. - Treat process.env as slow config storage, not fast runtime config. Bonus: Caching environment variables improves performance and protects against unexpected surprises. Environment variables can change at runtime, and reading them dynamically in hot code paths can cause indeterministic behavior. If you’re chasing performance and still reading process.env on the hot path, you’re not really chasing performance. You’re just pretending. You either care about perf, or you don’t. Pick a side.
